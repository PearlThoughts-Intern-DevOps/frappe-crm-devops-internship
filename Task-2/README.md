# Frappe CRM Backup and Restore Tool
 
A command-line tool that automates backup, verification, retention and restore for a Frappe CRM site running under Docker Compose. It uses only the Python standard library (Python 3.8+).
 
## What it does
 
- **backup**: runs `bench --site <site> backup --with-files` inside the bench container, copies the four backup files to the host, writes a SHA-256 manifest, then applies retention.
- **verify**: recomputes SHA-256 for every file in a backup and compares it with the manifest. Exit code 2 if anything is missing or does not match.
- **restore**: verifies the backup first, then restores it into a separate test site (default `test.localhost`). It refuses to restore over the source site.
- **cleanup**: keeps only the newest N backups (default 7). It also runs automatically after every backup.
- **list**: shows the stored backups.
Every run writes to a log file and produces a JSON report.
 
## Environment this was built for
 
- Docker Compose project from the `docker/` folder of this repository (services: `frappe`, `mariadb`, `redis`)
- Site `crm.localhost`, bench path `/home/frappe/frappe-bench` inside the `frappe` container
- Run on the Docker host (an Ubuntu EC2 instance in my case)
## Setup
 
1. Make sure the containers are running: `cd docker && docker compose ps`
2. Make sure your user can run `docker` without sudo.
3. Export the MariaDB root password used by the compose setup (needed for restore only):
```
   export DB_ROOT_PASSWORD=<mariadb root password>
```
 
## Usage
 
```
python3 backup_tool.py backup
python3 backup_tool.py verify                 # latest backup
python3 backup_tool.py verify --timestamp 20261104_200503
python3 backup_tool.py restore                # latest backup into test.localhost
python3 backup_tool.py restore --timestamp 20261104_200503 --target test.localhost
python3 backup_tool.py cleanup --keep 7
python3 backup_tool.py list
```
 
Options that apply to every command: `--compose-dir` (default `~/frappe-crm-devops-internship/docker`), `--backup-root` (default `~/frappe-backups`), `--site`, `--service`, `-v`.
 
## Where things are stored
 
```
~/frappe-backups/
  backups/<timestamp>/   the 4 backup files + manifest.json
  reports/               backup_*.json, verify_*.json, restore_*.json
  logs/backup_tool.log
```
 
One backup is a set of four files sharing a timestamp: database dump, public files, private files and the site config. Retention counts sets, not individual files.
 
## Exit codes
 
- 0 success
- 1 error (the message is logged)
- 2 verification failed (checksum mismatch or missing file)
## Design notes
 
- **Restore never touches the source site.** The target must differ from `--site`, and the tool creates the test site if it does not exist.
- **Restore verifies first.** A backup that fails its checksum check is not restored.
- **Version compatibility step.** In my environment, the database dump written by the MariaDB client in the bench image contains two `NOTE_VERBOSITY` lines that the `mariadb:10.8` server rejects, so a plain restore failed with `ERROR 1193`. During restore the tool removes those two lines from a temporary copy and restores from the copy. The original backup and its checksum are never modified. Use `--no-sanitize` to skip this step. The proper fix is matching the MariaDB client and server versions.
- **Related setup issue.** On my setup the bench image's MariaDB client required SSL while the MariaDB 10.8 server did not support it. I worked around it with a client config (`skip-ssl`) inside the running container. This is outside the tool and is not changed in the repository.
- Commands are run as argument lists (no `shell=True` on the host). Values passed into the container shell are quoted.
## Limitations
 
- Retention applies to the host copies. Bench's own backup folder inside the container is not pruned by this tool.
- The root password is passed on the command line to `bench` inside the container, so it is visible in the container's process list while the command runs. The tool masks it in its own logs and error messages. This is acceptable for a local lab, not for production.
- Backup folder names use the container's clock, while log lines use the host's clock. They can differ by the timezone offset (here UTC on the host vs IST in the container).
- Docker does not restart the containers automatically after the host reboots (no restart policy in the compose file). Run `docker compose start` before using the tool.
- A SHA-256 check proves the files were not corrupted after the backup. It does not prove the backup is restorable. That is what the restore step into the test site is for.
- Tested on one environment (the one described above).
