Phase 1: Foundation, Locking & Dual-Context Execution
Before touching backup files, your script needs to know where it is running, prevent overlapping cron runs, and establish structured logging.

1. Process Locking (fcntl)
If a scheduled cron backup takes longer than expected or hangs on a database lock, a second cron instance could trigger and delete files while the first is still reading them.

How to implement: Use Python's built-in fcntl.flock(lock_file, fcntl.LOCK_EX | fcntl.LOCK_NB) on /tmp/frappe_backup_manager.lock. If another instance holds the lock, catch BlockingIOError, log a warning, and exit cleanly.

2. Resolving the Host vs. Container Split (BenchRunner)
When you run bench backup, Frappe executes inside the container (crm-frappe-1) at /home/frappe/frappe-bench. However, if you run backup_manager.py from your host machine, Python's pathlib.Path looks at your host filesystem, while docker exec looks inside the container filesystem.

The Architecture Choice: Design BenchRunner to detect its environment automatically using shutil.which("bench"):

Mode A (Inside Container / Native Server): shutil.which("bench") returns a valid path. Both subprocess.run(["bench", ...]) and Python's Path() operate directly on /home/frappe/frappe-bench/sites/....

Mode B (Host Hybrid Mode via Docker): bench is not in $PATH. You pass --bench-dir pointing to the host's mounted sites directory (or execute the script directly inside the container via docker exec -it crm-frappe-1 python3 /home/frappe/frappe-bench/scripts/backup_manager.py).

Phase 2: Atomic Backup Set Discovery (BackupSet & RetentionPolicy)
Frappe does not have a concept of a "Backup Set" object—it just dumps loose files into private/backups/. Your script must reconstruct that abstraction from the filenames on disk.

1. The Regex Grouping Mechanism
Every file generated by bench backup --with-files follows a strict naming convention:<YYYYMMDD_HHMMSS>-<site_slug>-<artifact_type>

Why this matters: If you sort all files by modification time (st_mtime) and delete the oldest, you might delete a site_config_backup.json while keeping its corresponding database.sql.gz. Grouping by the 15-character timestamp prefix (YYYYMMDD_HHMMSS) guarantees atomic operations.

2. Data Model (BackupSet)
Create a @dataclass that represents a single point-in-time snapshot:

Python
@dataclass
class BackupSet:
    timestamp: str
    site: str
    database: Optional[Path] = None
    public_files: Optional[Path] = None
    private_files: Optional[Path] = None
    site_config: Optional[Path] = None
    manifest: Optional[Path] = None
    checksum_file: Optional[Path] = None

    @property
    def core_artifacts(self) -> dict[str, Optional[Path]]:
        return {
            "database": self.database,
            "public_files": self.public_files,
            "private_files": self.private_files,
            "site_config": self.site_config,
        }

    @property
    def is_complete(self) -> bool:
        # A valid --with-files backup must have all 4 core files present on disk
        return all(p is not None and p.exists() for p in self.core_artifacts.values())
3. Discovery & Grouping Algorithm
Scan config.backup_dir.iterdir().

Match each filename against rf"^(\d{{8}}_\d{{6}})-{config.site_slug}-(.+)$".

Extract group(1) as the timestamp key and group(2) as the suffix:

database.sql.gz 
→ BackupSet.database

files.tar 
→ BackupSet.public_files

private-files.tar 
→ BackupSet.private_files

site_config_backup.json 
→ BackupSet.site_config

manifest.json 
→ BackupSet.manifest

checksums.sha256 
→ BackupSet.checksum_file

Sort the dictionary keys in descending lexicographical order (sorted(sets.keys(), reverse=True)). Because timestamps are YYYYMMDD_HHMMSS, alphabetical sorting is guaranteed to equal chronological sorting.

Phase 3: Deep Verification & Manifest Engine (IntegrityVerifier)
A file having a SHA-256 hash only proves the file hasn't changed since the hash was recorded. What if mysqldump failed halfway through creating the .sql.gz file due to a full disk, and your script immediately hashed the broken file? To prevent hashing corrupt backups, verification must happen in two stages: Structural Validation (at creation) and Cryptographic Validation (at creation and before restore).

1. Stage A: Structural Validation (Deep Format Check)
Before generating a manifest for a new backup, inspect the internal structure of all four artifacts:

database.sql.gz: Open with gzip.open(path, "rb") and read in 64 KB chunks to the end of the stream. Unlike checking only the first 2 magic bytes (\x1f\x8b), reading the stream forces zlib to verify the CRC32 checksum and uncompressed size stored in the last 8 bytes (the gzip trailer). If the dump was truncated, gzip raises EOFError.

files.tar & private-files.tar: Open with tarfile.open(path, "r") and call .getmembers() to verify the TAR headers are not truncated.

site_config_backup.json: Parse with json.loads() and assert that "db_name" and "db_password" keys exist.

2. Stage B: Streaming SHA-256 & Dual Manifest Generation
Once structural checks pass:

Stream each of the 4 files in 64 KB blocks (65536 bytes) into hashlib.sha256(). This keeps RAM usage flat at ~64 KB regardless of whether the database is 5 MB or 50 GB.

Write <timestamp>-<site_slug>-manifest.json containing file sizes, hashes, UTC creation time, and verification status.

Write <timestamp>-<site_slug>-checksums.sha256 formatted with standard two-space separation (<hash>  <filename>) so standard Linux sha256sum -c works out of the box.

Phase 4: Retention Pruning Engine (RetentionPolicy)
Pruning should be the simplest module because Phase 2 already grouped everything into BackupSet objects.

Implementation Rules:
Filter Only Complete Sets: When counting the 7 latest backups to retain, only count sets where backup_set.is_complete is True. Do not let a failed partial backup push a healthy old backup out of the retention window.

valid_sets = [s for s in all_sorted_sets if s.is_complete]

Atomic Unlink: For every BackupSet in to_prune, iterate over its core artifacts plus manifest and checksum_file, calling path.unlink(missing_ok=True). Support a --dry-run flag that logs the exact filenames and bytes that would be freed without deleting them.

Phase 5: Safe Disaster Recovery Orchestrator (RestoreManager)
This is the most critical operational phase. Restoring a production CRM backup onto crm-test.localhost requires neutralizing background side-effects and syncing cryptographic keys.

Step-by-Step Execution Flow:
Pre-Flight Checksum Gate: Run IntegrityVerifier.verify_backup_set(target_set). If any file fails its SHA-256 check or structural gzip/tar check, raise VerificationError and abort immediately before touching the test site.

Site Bootstrap Check: Check if sites/crm-test.localhost exists. If not, bootstrap it automatically:

Bash
bench new-site crm-test.localhost --mariadb-root-password <pwd> --admin-password admin --no-mariadb-socket
Execute Native Restore: Run the bench restore command passing all three data artifacts explicitly:

Bash
bench --site crm-test.localhost restore <path/to/db.sql.gz> \
  --with-public-files <path/to/files.tar> \
  --with-private-files <path/to/private-files.tar> \
  --mariadb-root-password <pwd> \
  --force
Neutralize Background Workers (Crucial Safety Step): Immediately disable the scheduler so the test site does not send emails or trigger webhooks using production data:

Bash
bench --site crm-test.localhost scheduler disable
Sync encryption_key: Read encryption_key from the backup's site_config_backup.json and update sites/crm-test.localhost/site_config.json (preserving the test site's db_name and db_password while replacing encryption_key). Without this, Frappe cannot decrypt OAuth tokens or SMTP passwords stored in the database.

Clear Cache & ORM Smoke Test:
